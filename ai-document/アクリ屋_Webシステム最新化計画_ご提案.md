# アクリ屋 Webシステム最新化計画 ご提案

- 作成日: 2026年11月22日
- 対象: さくら樹脂御中
- 版: 1.0

> **2名体制・約2か月（8週間）で、PHP 7.2 / Laravel 5.8 のシステムを PHP 8.5 / Laravel 13 へ。**
> URL・画面・SEO・カートは維持し、AWS上に新しい本番環境を構築します。

---

## 0. ご提案の概要

### はじめに

御社のECサイト「アクリ屋」で稼働している商品管理システムは、現在PHP 7.2とLaravel 5.8で動いています。どちらもサポートが終了しており、このまま使い続けると、セキュリティ上の不安が残るだけでなく、ちょっとした変更にも時間がかかる状態です。

一方で、このシステムは日々の商品登録や受注に欠かせないため、長期間止めることはできません。そこで、動いている状態を保ちながら、少しずつ新しい技術へ移行する計画をご提案します。

具体的には、商品管理のプログラムをLaravel 13へ、プログラムを動かすPHPを8.5へ段階的に更新し、本番環境をAWS（クラウド）上に新しく構築します。作業は2名で分担し、約2か月（8週間）を想定しています。1名がLaravel / PHPの更新を、もう1名がAWS環境の構築を担当し、要所で互いに支え合いながら進めます。

更新は一度にまとめて行うのではなく、Laravelを1つずつ新しいバージョンに上げ、その都度テストと画面確認を行います。本番環境の切り替えも、十分な検証と、万一のときに元の環境へ戻せる準備ができてから実施します。URL、画面、SEO、カートの仕組みはこれまでどおり維持するため、お客様や社内の使い勝手は変わりません。

この資料では、なぜ最新化が必要なのか、何を変えて何を変えないのか、どのような順序と期間で進めるのかを、順にご説明します。

### ご提案の3つのポイント

1. **アプリを最新化する** — Laravel 5.8 → 13。1バージョンずつ上げ、回帰リスクを最小化します。
2. **実行基盤を刷新する** — PHP 7.2 → 8.5。AWS上に Apache + PHP-FPM で構築します。
3. **止めずに移行する** — 段階リリースと切戻しで、業務を止めずに切り替えます。

### 計画の概要

| 項目 | 内容 |
|---|---|
| 期間 | **約2か月（8週間）** |
| 体制 | **2名**（Laravel / PHP 主担当、本番環境 主担当。要所で相互支援） |
| 移行元 | PHP 7.2 / Laravel 5.8 |
| 移行先 | **PHP 8.5 / Laravel 13 / AWS** |
| 維持するもの | 6ドメイン、URL、画面、SEO、カートCGI |

## 1. 現状と課題

### 現状

| 項目 | 現状 | 課題 |
|---|---|---|
| PHP | 7.2 | サポート終了。セキュリティ修正が提供されない |
| Laravel | 5.8 | 古い依存が多く、変更のたびに調査が必要 |
| 本番環境 | 現行サーバー（さくら）+ RDS | 手作業中心で、障害対応・拡張が難しい |
| ドメイン | 本番・検証あわせて6ドメイン | URL・SEOを維持したまま移行する必要がある |
| カート | Perl / CGI | 機能変更はできない。止められない |

### 事業への影響

- **セキュリティ**: サポート切れにより、脆弱性が残るリスク
- **保守性**: 古い依存と独自設定が多く、変更に時間がかかる
- **性能・拡張性**: アクセス増加に備えたスケールがしにくい
- **採用・パートナー**: 最新スキルを持つ人材・ベンダーを確保しにくい

> **業務は止められない。だから、段階的に進める。**

## 4. Laravel バージョンアップ計画

### 基本方針

- **1バージョンずつ**上げ、変更の原因を切り分ける
- **Phase 0** でテスト・画面・URLの基準を固定する
- 各フェーズでテスト、スクリーンショット比較、DBバックアップ、Gitタグを実施する

### フェーズ一覧

| Phase | Laravel | 主な内容 | 目安 |
|---|---|---|---|
| 0 | 5.8 | ベースライン構築（テスト・画面・URL記録） | 10–15日 |
| 1 | 6.x | helper、laravel/ui、不要パッケージ削除 | 5日 |
| 2 | 7.x | Symfony 5、`getClientSize()` | 3日 |
| 3 | 8.x | factory / seeder、faker、Throwable | 8日 |
| 4 | 9.x | Symfony Mailer、Flysystem 3、lang移動 | 8日 |
| 5 | 10.x | `$dates` → `$casts`、Monolog 3、PHPUnit 10 | 5日 |
| 6 | 11.x | アプリ構造、Formファサード、config化 | 15日 |
| 7 | 12.x | Carbon 3、PHPUnit 11 | 3日 |
| 8 | 13.x | CSRF、session、PHP 8.5対応 | 8日 |
| 9 | 13.x | 性能、セキュリティ、本番切替 | 10日 |

### 難所

- 管理画面のフォーム **約800箇所**（`Form::` 788箇所）
- PHP 8系の非互換 **110箇所**（動的プロパティ81、暗黙nullable12、null渡し17）
- 既存テストは72件。Phase 0で特性テストと画面比較を追加する

### 工数

- **75–80人日**（両アプリ、1名想定）
- **2名で分担し、8週間で完了する想定**（要所で相互支援）

## 5. PHP バージョンアップ計画

### バージョンの進め方

| PHP | Laravel | 主な対応 |
|---|---|---|
| 7.2 | 5.8 / 6 | ベースライン、現状固定 |
| 7.4 | 6 / 7 | 削除関数、型宣言の整合 |
| 8.0 | 8 / 9 | factory / seeder、Throwable |
| 8.1 | 9 / 10 | Symfony Mailer、Flysystem 3 |
| 8.2 | 10 / 11 / 12 | `$casts`、Monolog 3、Form準備 |
| 8.3 | 11 / 12 / 13 | アプリ構造、Formファサード |
| **8.5** | **13** | **最終目標。PHP 8.5対応、CSRF、session** |

### 基本方針

- Laravelの要件に合わせ、**最小差分**でPHPを上げる
- PHP 8系の非互換を事前に検出する（**110箇所**）
- 各フェーズで**非推奨警告0件**を目指す
- **PHP 8.6は採用しない**（Laravelの安定性を優先）

### 品質ゲート

各フェーズで以下を満たした場合のみ次へ進みます。

- [ ] `php -l` で構文エラーがない
- [ ] PHPUnit が green
- [ ] 主要導線のブラウザテストが通る
- [ ] 画面スクリーンショットが Phase 0 と一致
- [ ] 非推奨警告・警告・致命的エラーがない
- [ ] `composer audit` に致命的な脆弱性がない
- [ ] DBバックアップとGitタグがある

## 6. 本番環境実装計画

### 全体構成

```
Internet
   │
Route53（DNS）
   │
AWS WAF（防御）
   │
ALB（負荷分散）
   │
EC2（Apache + PHP-FPM 8.5 / Perl 5.32 CGI）
   ├── RDS MySQL 8.4（既存を活用）
   └── EFS（商品画像・レビュー画像・CSV）
```

### 6ドメイン

| 環境 | ドメイン |
|---|---|
| 本番 | `acry-ya.com` / `admin.acry-ya.com` |
| 検証 | `test.acry-ya.com` / `test-admin.acry-ya.com` |
| 開発 | `dev.acry-ya.com` / `dev-admin.acry-ya.com` |

### コンポーネント

| レイヤ | 構成 | 役割 |
|---|---|---|
| LB | ALB + WAF | 負荷分散、防御、HTTPS終端 |
| コンピュート | EC2（本番2台 / 検証1台） | Apache + PHP-FPM、Perl CGI |
| 共有ストレージ | EFS | 商品画像・レビュー画像・CSVの共有 |
| DB | RDS MySQL 8.4（既存） | 商品DB・受注DB |
| デプロイ | S3 + CodeDeploy | 自動デプロイ、ロールバック |
| 監視 | CloudWatch + Synthetics | メトリクス、ログ、外形監視 |
| セキュリティ | WAF / GuardDuty / Patch Manager | 防御、検出、パッチ適用 |

### 4つのステージ

| ステージ | Phase | 主な作業 |
|---|---|---|
| 1. 設計・基盤 | 0–2 | 現状調査、CDK、サーバー標準イメージ |
| 2. 構築・移行 | 3–5 | EFS、ALB、6ドメイン、CGI |
| 3. 自動化・監視 | 6–7 | CI/CD、自動デプロイ、監視 |
| 4. 本番切替 | 8–9 | DNS切替、スモークテスト、安定化 |

### ポイント

- **現行URL・.htaccess・CGIを維持**する
- **既存RDSを活用**し、データ移行リスクを最小化する
- **CDK + CI/CD + 監視/バックアップ**を標準装備する
- **AI（MCP）** で設計・検証を標準化し、構築を加速する

## 8. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 画面・業務の互換性 | 操作が変わってしまう | 特性テストとスクリーンショット比較で差分を確認 |
| DB・暗号化データ | データが読めない | フェーズごとにバックアップ。APP_KEYを維持 |
| CGI・WordPress | カート・ブログが動かない | 事前に依存を棚卸し。旧環境へのフォールバックを用意 |
| 切替失敗 | サービス停止 | DNS切戻しを準備。旧環境は2〜4週間保持 |
| スケジュール遅延 | リリース延期 | フェーズゲートと並行作業で、遅れを早期に検知 |

> **各フェーズに「次へ進む条件」を設定し、リスクを先に潰す。**
