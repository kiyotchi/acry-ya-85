## 0. 決定事項サマリ

| 項目 | 決定 | 理由 |
|---|---|---|
| コンピューティング | **EC2 + ALB**（Auto Scaling Group） | Apache + PHP-FPM、1,789行の `.htaccess`、Perl/CGI をそのまま再現できる。ECS 化は将来の最適化として保留 |
| IaC | **AWS CDK (TypeScript)** | AWS IaC MCP と相性が良く、型補完・テスト・cdk-nag が使える |
| データベース | **既存 RDS を継続** | prod 用 `mysql84` と test/dev 用 `acry-ya-db` の2系統が既に存在。移行リスクを下げる |
| AWS アカウント | **既存アカウント（管理者権限あり）** | 既存 VPC / RDS / Route53 を再利用する |
| Web サーバー | **Apache 2.4 + PHP-FPM（event MPM）** | AL2023 の標準構成。`.html` を PHP 実行する部分は vhost の `SetHandler` で再現する |
| PHP | **8.5（AL2023 の `php8.5` / `php8.5-fpm`）** | 2026年1月以降 AL2023 の dnf で提供 |
| Perl | **5.32（AL2023 のシステム Perl）** | 5.44 のソースビルドは不要。CGI の CPAN モジュールと shebang のみ対応 |
| 環境分離 | prod 用 ASG（2台）と test/dev 用 ASG（1台）を分離 | 本番の安定性と非本番の自由度を両立。同一 ALB でホスト名ルーティング |
| デプロイ | **GitHub Actions → S3 → CodeDeploy** | ASG + ALB のローリングデプロイとロールバックを標準化 |
| 共有ファイル | **EFS** | 商品画像・レビュー画像・在庫CSVを複数インスタンスで共有 |
| 監視 | CloudWatch + Synthetics + SNS | AWS 標準で十分。追加 SaaS は不要 |
| MCP | **AWS MCP Server（読み取り専用）+ AWS IaC MCP + GitHub MCP + Playwright MCP** | 設計・検証・デプロイ確認を AI で自動化。変更系は人間が承認 |

## 1. ゴールとスコープ

### 1.1 ゴール

`本番インフラ.md` の要件を満たす AWS 環境を、CDK で再現可能に構築する。

- Amazon Linux 2023
- PHP 8.5.x
- Apache 2.4 + PHP-FPM（event MPM）
- Perl 5.32（CGI）
- 6 バーチャルホスト
  - `acry-ya.com` / `admin.acry-ya.com`
  - `test.acry-ya.com` / `test-admin.acry-ya.com`
  - `dev.acry-ya.com` / `dev-admin.acry-ya.com`
- 既存 RDS（MySQL 8.4）への接続
- 画像・CSV の共有、バックアップ、監視、CI/CD、ロールバックを含む

### 1.2 スコープ外

- Laravel 5.8 → 13 のコード改修（`laravel-upgrade.md`）
- カート CGI の機能改修（新サーバーでの**現状動作の維持**のみ）
- WordPress（`public/_blog`）の機能改修
- 商品画像の編集機能そのものの変更
- さくらサーバーの契約解除（カットオーバー安定後）

### 1.3 最重要の前提：アプリ移行との順序

**新しい本番環境は PHP 8.5 / Laravel 13 専用**であり、現行の Laravel 5.8 は PHP 8.5 では動作しない。

したがって、次の順序を守る。

1. インフラ構築と Laravel 移行を**並行**して進める。
2. 新インフラの test/dev 環境で、Laravel 13 / PHP 8.5 の 85 系アプリを検証する。
3. `laravel-upgrade.md` の **Phase 8（Laravel 13 / PHP 8.5）完了**をカットオーバーの前提条件とする。
4. 本番カットオーバーは Phase 9（安定化）と同時期に行う。
5. 中間フェーズ（Laravel 6〜10）の検証は、引き続きローカル Docker で行う。

> AL2023 は PHP の複数バージョン同居ができない（`php8.5*` と `php8.1*` は競合）。
> 中間フェーズ用に別 AMI を作ることは可能だが、本計画では対象外とする。

### 2.4 ネットワーク / セキュリティグループ

| SG | Ingress | 備考 |
|---|---|---|
| `sg-alb` | 80, 443 from `0.0.0.0/0` | WAF 経由 |
| `sg-app` | 80 from `sg-alb` | ALB → EC2 |
| `sg-app` | 2049 from `sg-app` | EFS |
| `sg-rds` | 3306 from `sg-app` | 既存 RDS の SG に追加 |

- IMDSv2 必須。
- EBS / EFS / S3 は暗号化。

### 2.5 ストレージ設計（EFS）

EFS を 1 つ作成し、アクセスポイントで用途を分ける。

| EFS パス | マウント先（例） | 用途 | 移行元 |
|---|---|---|---|
| `/images` | `/mnt/efs/images` → 管理 `storage/app/public/img_storage` / フロント `public/storage/images` | 商品画像 | 管理 760MB |
| `/reviewimages` | `/mnt/efs/reviewimages` → フロント `public/storage/reviewimages` | レビュー画像 | フロント 26MB |
| `/data` | `/mnt/efs/data` → 各 vhost の `data/` | `zaiko6.csv` | 各環境 |
| `/shared` | `/mnt/efs/shared` → `storage/framework` 等（任意） | 共有キャッシュ | 必要に応じて |

- EFS は `nfsvers=4.1`、TLS、`_netdev` でマウント。
- POSIX 権限は Apache 実行ユーザー（AL2023 は `apache`、uid 48）に合わせる。
- 画像は**デプロイ artifact に含めない**。EFS に一度移行し、以後は管理画面のアップロードで更新する。
- `storage/logs` とセッションはローカル（インスタンス単位）。ログは CloudWatch Agent で転送。

`DELIVERIES_PATH` が `/var/www/<vhost>/data/zaiko6.csv` を指すため、**パスは現行に合わせる**。

```
│   │       ├── storage -> ../../shared/storage
```

- Apache の `DocumentRoot` は `/var/www/<vhost>/current/public`。
- `AllowOverride All` を設定（1,789行の `.htaccess` を有効にするため）。
- `Options +ExecCGI` を vhost に設定（`.htaccess` の `#Options +ExecCGI` はコメントアウトされているため）。
- `.env` は SSM Parameter Store からデプロイ時に生成。**artifact に含めない**。
- `APP_KEY` は現行の値をそのまま使う（暗号化データの互換性のため変更禁止）。

### 2.7 ランタイム構成

#### PHP 8.5（PHP-FPM）

```bash
# パッケージ名は導入時に dnf で確認する
dnf list available 'php8.5*'
dnf install -y httpd php8.5 php8.5-fpm php8.5-cli \
  php8.5-mysqlnd php8.5-mbstring php8.5-gd php8.5-xml \
  php8.5-bcmath php8.5-intl php8.5-opcache php8.5-process \
  php8.5-curl php8.5-zip mod_ssl
```

- 必須拡張: `pdo_mysql`, `mbstring`, `gd`, `exif`, `bcmath`, `intl`, `opcache`
- `exif` はパッケージ構成を確認し、なければ PECL またはビルドオプションで対応。
- AL2023 の既定は **event MPM + PHP-FPM**。`php8.5-fpm` を入れると Apache は `mod_proxy_fcgi` 経由で `/run/php-fpm/www.sock` に接続する。
- `php-fpm.d/www.conf`:
  - `listen = /run/php-fpm/www.sock`
  - `listen.owner = apache`, `listen.group = apache`, `listen.mode = 0660`
  - `pm = dynamic`, `pm.max_children = 40`（t3.medium / 4GB の目安。負荷試験で調整）
  - `pm.start_servers = 5`, `pm.min_spare_servers = 5`, `pm.max_spare_servers = 10`
  - prod と nonprod でプールを分ける場合は、別 socket と `open_basedir` を設定する
- **`.html` / `.htm` を PHP 実行する設定**:
  - `.htaccess` の `AddType application/x-httpd-php .html .htm` は FPM では効かない
  - vhost に以下を追加する（`.htaccess` は変更しない）:
    ```apache
    <FilesMatch "\.(html|htm)$">
      SetHandler "proxy:unix:/run/php-fpm/www.sock|fcgi://localhost"
    </FilesMatch>
    ```
  - これで現行と同じく、すべての `.html` が PHP として実行される
  - `.htaccess` に `php_value` / `php_flag` があると FPM では 500 になる。事前に grep で確認する（現状は 0 件）
- `php.ini`（本番）:
  - `memory_limit=256M`
  - `upload_max_filesize=20M` / `post_max_size=20M`
  - `max_execution_time=60`
  - `date.timezone=Asia/Tokyo`
  - `expose_php=Off`
  - `opcache.enable=1`, `opcache.validate_timestamps=0`, `opcache.memory_consumption=128`
- `opcache.validate_timestamps=0` のため、デプロイ時は `systemctl reload php-fpm` を実行する。
- Apache の `MaxRequestWorkers` は event MPM の既定（`ThreadsPerChild 25` × `ServerLimit`）を基準にし、FPM の `pm.max_children` とバランスさせる。

#### Apache 2.4

- 有効モジュール: `proxy`, `proxy_fcgi`, `rewrite`, `headers`, `cgi`, `cgid`, `ssl`, `expires`, `deflate`, `setenvif`, `alias`, `access_compat`, `remoteip`
- vhost 共通設定:
  - `AllowOverride All`
  - `Options -Indexes +FollowSymLinks +ExecCGI`
  - `SetEnvIf X-Forwarded-Proto https HTTPS=on`（ALB の TLS 終端対策）
  - `RemoteIPHeader X-Forwarded-For`（ログの実 IP）
  - `Header always set Strict-Transport-Security "max-age=31536000"`（本番のみ）
  - `.html` / `.htm` の `SetHandler "proxy:unix:/run/php-fpm/www.sock|fcgi://localhost"`
- `.htaccess` の主要ディレクティブ（実測）:
  - `RewriteRule` 1,677 行 / `RewriteCond` 21 行
  - `AddHandler cgi-script .cgi .pl`
  - `AddType application/x-httpd-php .html .htm`（FPM では vhost の `SetHandler` で代替）
  - `Header`, `ErrorDocument`, `Options`
  - → `mod_rewrite`, `mod_headers`, `mod_cgid`, `mod_proxy_fcgi` が必須。`mod_php` は使わない。

#### Perl 5.32（システム Perl）

AL2023 の dnf で提供される Perl 5.32 をそのまま使う。5.44 のソースビルドは不要。

```bash
dnf install -y perl perl-CPAN
/usr/bin/perl -v   # 5.32.x
```

- 既存 CGI の shebang は `#!/usr/bin/perl` と `#!/usr/local/bin/perl` が混在。
  - `#!/usr/bin/perl` はそのまま動く。
  - `#!/usr/local/bin/perl` のために `/usr/local/bin/perl` を `/usr/bin/perl` への symlink にする。
  - `ip.cgi` の先頭に UTF-8 BOM がある場合は除去（BOM があると shebang が認識されない）。
- CPAN モジュールは現行サーバーで `perl -M<module>` の一覧を取得し、`cpanm` で導入する。
  - `CGI.pm` など、Perl 5.32 の core に含まれないモジュールは CPAN から入れる。
- 各 CGI は `perl -c` で構文チェックし、ステージングで実行確認する。
- `本番インフラ.md` の Perl 要件は 5.32 に更新済み（合意済み）。

### 2.8 既存 RDS の利用

| 環境 | RDS | DB | 備考 |
|---|---|---|---|
| prod | `mysql84` | `acryya_system` | 既存。カットオーバーまで読み取りのみ |
| test | `acry-ya-db` | `test_acryya_system` | 既存 |
| dev | `acry-ya-db` | `dev_acryya_system` | 既存 |

- 新 EC2 の SG から既存 RDS の SG へ 3306 を許可する。
- RDS が別 VPC の場合は VPC Peering を追加（Phase 0 で判定）。
- PHP 8.5 の mysqlnd は `caching_sha2_password` に対応。`mysql_native_password` への依存は不要。
- 接続は TLS を推奨。CA 証明書は RDS のグローバルバンドルを配置。
- テスト用 DB は本番ダンプをそのまま使わず、個人情報をマスキングしたダンプを使う。

### 2.9 DNS / TLS / メール

- Route53 に `acry-ya.com` ホストゾーンを作成（既存プロバイダーから移管、または ALIAS 相当で ALB を指す）。
- ACM で `acry-ya.com`, `www.acry-ya.com`, `admin.acry-ya.com`, `test.acry-ya.com`, `test-admin.acry-ya.com`, `dev.acry-ya.com`, `dev-admin.acry-ya.com` の証明書を取得。
- カットオーバー前に TTL を 60 秒へ短縮。
- メールは既存の `mail.acry-ya.com` を継続利用。EC2 からの 25 番ポートは throttling されるため、**587（STARTTLS）または SES** を使う。
- `admin.acry-ya.com` の `.env-prod` に `APP_DEBUG=true` が残っている。本番では必ず `false` に修正する。

### 2.10 監視 / バックアップ / セキュリティ

- CloudWatch アラーム:
  - ALB: 5xx 率、TargetResponseTime、UnHealthyHostCount
  - EC2: CPU、Disk、StatusCheckFailed
  - EFS: BurstCreditBalance、PercentIOLimit
  - RDS: CPU、FreeableMemory、DatabaseConnections、FreeStorageSpace
- CloudWatch Synthetics で 7 URL を 5 分間隔で監視（ログイン画面、商品一覧、画像）。

- バックアップ:
  - RDS: 既存の自動バックアップを確認し、保持 7〜14 日。
  - EFS: AWS Backup で日次。
  - EBS: AWS Backup で日次。
  - S3: バージョニング + ライフサイクル。
- セキュリティ:
  - GuardDuty / Security Hub / Inspector を有効化。
  - SSM Patch Manager で月次パッチ。
  - WAF マネージドルール（Common, KnownBadInputs, SQLi）+ レート制限。
  - VPC Flow Logs、CloudTrail（全リージョン）。
  - S3 パブリックアクセスブロック。

## 3. MCP 構成

### 3.1 採用する MCP サーバー

| 名前 | 提供元 | 接続 | 主な用途 | 権限 |
|---|---|---|---|---|
| `aws-mcp` | AWS 公式（マネージド） | HTTP（OAuth）または stdio（SigV4 Proxy） | AWS API の参照、ドキュメント検索、構成確認、コスト確認 | **読み取り専用プロファイル** |
| `aws-iac` | AWS Labs | stdio（`uvx`） | CDK のドキュメント・サンプル・ベストプラクティス検索、CloudFormation 検証 | ローカル・読み取りのみ |
| `github` | GitHub 公式 | HTTP | Issue / PR / Actions の確認と作成 | PAT（`repo`, `workflow`） |
| `playwright` | Microsoft | stdio（`npx`） | 6 ドメインの E2E、スクリーンショット、リダイレクト検証 | ローカルブラウザ |
| `claude-mem` | 既存 | stdio | 決定ログ、作業履歴の記録 | ローカル |
| `mysql-ro`（任意） | コミュニティ | stdio | スキーマ・件数の読み取り確認 | **読み取り専用 DB ユーザー** |

**導入しないもの**

- `aws-api-mcp-server` / `aws-knowledge-mcp-server`: 公式 AWS MCP Server に統合済み。併用するとツールが競合するため削除する。
- Terraform MCP: Terraform を採用しないため不要。

### 3.2 導入手順（Claude Code）

前提: AWS CLI v2（2.32.0 以上）、`uv`、Node.js、`gh`。

```bash
# 0. ツール
brew install awscli        # または公式インストーラ
# uv は導入済み
npm install -g aws-cdk

# 1. AWS 認証（管理者）
aws login                  # または aws sso login --profile <profile>
aws sts get-caller-identity

# 2. AWS MCP Server（OAuth・単一アカウント向け）
claude mcp add aws-mcp https://aws-mcp.ap-northeast-1.api.aws/mcp --transport http

# 3. AWS MCP Server（SigV4・読み取り専用。推奨）
#    --read-only の有無は `uvx mcp-proxy-for-aws-cli@latest --help` で確認
claude mcp add-json aws-mcp-ro '{
  "type": "stdio",
  "command": "uvx",
  "args": [
```

### 3.3 権限とガードレール

**IAM プロファイルを 2 つに分ける。**

| プロファイル | 用途 | 権限 |
|---|---|---|
| `acryya-mcp-ro` | MCP からの参照 | `ReadOnlyAccess` + `AWSMCPSignInOAuthAccessPolicy`（OAuth を使う場合） |
| `acryya-deploy` | 人間が実行する `cdk deploy` | 管理者相当（`AdministratorAccess` または必要最小限のカスタムポリシー） |

**ルール**

1. MCP には**書き込み権限を渡さない**。`--read-only` と IAM の両方で制限する。
2. `cdk deploy` は MCP から実行しない。人間が `cdk diff` を確認してから実行する。
3. MCP のプロンプトに秘密情報（`.env` の値、DB パスワード、APP_KEY）を貼らない。SSM パラメータ名だけを渡す。
4. 本番 DB への書き込み権限を MCP に渡さない。`mysql-ro` を使う場合も `SELECT` のみ。
5. すべての AWS API 呼び出しは CloudTrail に記録される。作業前に CloudTrail が有効なことを確認する。
6. 決定事項と `cdk diff` の要約を `claude-mem` に記録し、レビュー可能にする。

| 3 | CGI の shebang / BOM | 500 エラー | `/usr/local/bin/perl` の symlink、BOM 除去、デプロイ時のチェック |
| 4 | PHP-FPM のプロセス不足 | レスポンス遅延 / 502 | `pm.max_children` を負荷試験で調整。t3.medium から開始 |
| 5 | `.htaccess` 1,789 行の非対応ディレクティブ | リダイレクト / ヘッダー欠落 | モジュールを網羅。ステージングで全 301 をクロール比較 |
| 6 | `.html` を PHP 実行する設定 | 一部ページが 500 / ソース表示 | vhost の `SetHandler "proxy:unix:..."` で再現。全 `.html` をスモークテスト |
| 7 | `_blog`（WordPress）の依存 | ブログが表示されない | DB / プラグインを棚卸し。困難なら CloudFront パスルーティングで旧環境へ |
| 8 | 画像・CSV の共有漏れ | 画像 404 / 在庫更新不整合 | EFS に集約。front/admin を同一インスタンスに配置 |
| 9 | ファイルセッション + 複数台 | ログインが切れる | ALB スティッキーセッション。将来 Redis / DB セッション |
| 10 | RDS が別 VPC | 接続不可 | Phase 0 で VPC を確認。Peering または同一 VPC へ配置 |
| 11 | DNS / SEO の一時的な順位低下 | 売上影響 | TTL 短縮、301 維持、Search Console 監視、切り戻し |
| 12 | コスト超過（NAT / EFS） | 予算超過 | 1 NAT から開始、VPC エンドポイント併用、Budgets アラーム |
| 13 | 秘密情報の漏洩 | セキュリティ事故 | SSM SecureString、KMS、Git 管理外、MCP に渡さない |
| 14 | MCP の誤操作 | 意図しない変更 | 読み取り専用プロファイル、`cdk diff`、人間の承認、CloudTrail |
| 15 | 管理画面 prod の `APP_DEBUG=true` | 情報漏洩 | 本番 `.env` を `false` に修正 |
| 16 | 巨大 artifact（1.2GB） | デプロイ遅延 | S3 マルチパート、静的資産を分離、EFS へ移行 |
| 17 | メール 25 番ポート制限 | メール不達 | 587 / SES を使用 |
| 18 | PHP 拡張の欠落（exif 等） | 画像処理エラー | AMI ビルド時に `php -m` で検証 |
| 19 | Laravel 13 のセッション仕様変更 | ログアウト | カットオーバー前に周知。`SESSION_COOKIE` を明示 |
| 20 | 旧環境の停止判断ミス | 切り戻し不能 | 2〜4 週間は旧環境を維持 |
| 21 | `.htaccess` の `php_value` / `php_flag` | FPM で 500 | grep で 0 件を確認済み。将来追加されたら vhost の `php_admin_value` へ移す |

## 12. 調査メモ（2026-11-22 時点）

- AL2023 は PHP 8.1〜8.5 を提供。PHP 8.5 は 2026 年 1 月のリリースで追加され、`php8.5` / `php8.5-fpm` が利用可能。複数バージョンの同居は不可。
- AL2023 の Perl は 5.32 固定。本計画では 5.32 をそのまま使う（5.44 のソースビルドは不要）。
- PHP は AL2023 の既定どおり **event MPM + PHP-FPM** を使う。mod_php は prefork 必須のため採用しない。
- `.html` を PHP 実行する現行仕様は、vhost の `SetHandler "proxy:unix:/run/php-fpm/www.sock|fcgi://localhost"` で再現する。
- AWS MCP Server は 2026 年 5 月に GA。`aws-api-mcp-server` と `aws-knowledge-mcp-server` を統合。読み取り専用モードは SigV4（MCP Proxy for AWS）で利用可能。
- AWS IaC MCP Server は CDK のドキュメント・サンプル・ベストプラクティス検索を提供するが、CDK の synth / deploy は行わない。検証はローカルの `cdk synth` / `cdk-nag` で行う。
